# BUNKER-disco — Спутник разработчика и журнал решений

Этот скилл является главным внутренним компасом агента при разработке проекта **BUNKER-disco**.  
Он гарантирует соблюдение всех принятых архитектурных стандартов, целостность документации и предотвращает расхождения между задуманным дизайном и кодом.

---

## 1. Фундаментальное правило: «Сначала документация»

Перед реализацией любого модуля, эндпоинта, компонента или механики:
1. **Проверь существующую документацию в `docs/`:**
   - Не придумывай новые форматы карточек или эндпоинты «из головы» — в `docs/` уже прописаны строгие контракты.
   - Соблюдай правила переноса карт и тегирования из [**`GEMINI.md`**](file:///c:/Папки/коды/BUNKER-disco/GEMINI.md).
2. **Если принято новое архитектурное решение:**
   - Сразу зафиксируй его в соответствующем документе `docs/` и добавь запись в этот скилл (раздел [Журнал решений](#3-журнал-архитектурных-и-геймплейных-решений)).

## 3. Журнал архитектурных и геймплейных решений (ADR)

### ADR-01: Двухфазный игровой цикл
* **Решение:** Игра строго делится на две фазы. Первая — **Отбор** (социальная дедукция, дебаты, открытие карт, голосования у входа). Вторая — **Выживание** (30 дней внутри запечатанного бункера с распределением на работы, кризисами и расходом ресурсов).
* **Следствие:** Игроки обязаны думать об экосистеме выживания, а не просто голосовать «по дружбе».

### ADR-02: Вместимость бункера $\lfloor N / 2 \rfloor$ и лимит до 20 игроков
* **Решение:** Поддержка комнат от 4 до 20 игроков. Вместимость убежища рассчитывается по строгому настольному правилу: **ровно половина участников с округлением вниз**:
  $$K = \lfloor N / 2 \rfloor$$
* **Следствие:** При 20 игроках мест ровно 10; при 11 игроках — 5; при 7 — 3.

### ADR-03: Роль ведущего — бессменный ПК-автомат + Редактор таймлайна
* **Решение:** Ведущим всегда выступает сам сервер (ПК). Он озвучивает раунды, ведёт таймеры, производит подсчёт голосов и драматические изгнания.
* **Следствие:** Хост может запустить процедурную случайную партию либо через **Scenario Builder** выставить кастомный 30-дневный таймлайн кризисов.

### ADR-04: Конфигурируемость колод и перерандом в лобби
* **Решение:**
  * Колода «Суперсилы» по умолчанию отключена (`enableSuperpowers: false`) для реализма, включается для пати-режима.
  * Параметр `rerollLimit: number` (по умолчанию 1) определяет, сколько раз игрок в лобби может перерандомить персонажа, если стартовая раздача кажется ему безнадёжной.

### ADR-05: Визуальный «вайб физических карточек» (Card Vibe)
* **Решение:** Все данные персонажа, инвентарь и открытая информация других игроков визуализируются как **коллекционные физические карточки**:
  * 3D переворот (flip), тиснение, фольгированные рамки по редкости/категориям, рубашки карт для закрытых данных.
  * При генерации или перерандоме персонажа карты со звуком «слайда колоды» раздаются рубашкой вверх и эффектно переворачиваются.
  * При осмотре досье другого игрока открывается интерактивный веер/раскладка его открытых карт.

### ADR-06: 3D воксельная сцена на ТВ с Туманом Войны
* **Решение:**
  * Фаза 1: сцена на поверхности (лес, костёр, гермодверь). Разрез подземного бункера затянут динамическим **Fog of War**. При открытии карты комнаты туман рассеивается, и комната материализуется из воксельных блоков.
  * Фаза 2: запечатывание дверей, переход персонажей внутрь, где они перемещаются по комнатам и устраняют поломки.

### ADR-07: CQRS-lite архитектура бэкенда
* **Решение:** API обслуживает только чтение (GET) и отправку действий в очередь Redis (`POST /actions`). Вся логика выполняется пулом фоновых воркеров строго **последовательно для одной комнаты (Redis lock)** и **параллельно между разными комнатами**.

### ADR-08: Запуск всего стека через Docker Compose
* **Решение:** Полная изоляция в 5 контейнерах (`frontend`, `api`, `worker`, `redis`, `mongo`) одной командой `docker compose up -d`.

## 4. Памятка для агента при добавлении нового функционала

1. Всегда обращайся к этой инструкции перед началом задачи.
2. Не ломай существующие типы карточек и API контракты.
3. Сохраняй pixel RPG стилистику UI и воксельную визуализацию сцены.
4. При изменениях синхронизируй `docs/` и данный файл.
